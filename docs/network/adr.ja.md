# アーキテクチャ決定記録 (ADR) - Rettle Network サブシステム

[English](adr.md)

本書は、Rettle ETL フレームワークにおける通信サブシステム `Rettle::Network` に関して策定されたアーキテクチャおよび設計上の決定事項を記録したものです。

---

## ADR-NET-001: トランスポート非依存のチャネル抽象化

### ステータス
承認済み (Accepted)

### コンテキスト
ETL パイプラインの各タスク（Extract, Transform, Load）は、単一の Ruby プロセス内のスレッド間、独立した子プロセス間、あるいは将来的なリモート分散ノード間など、多様な実行境界を越えてデータをストリーミングする必要があります。タスクの実装が特定の並行処理プリミティブ（例: `Thread::Queue#push` の直接呼び出しやファイルディスクリプタの直接読み取り）に密結合している場合、並行実行モデルの切り替えやリモートワーカーの導入時に、ユーザー向けのタスク定義やオーケストレーションロジックの大幅な改修が必要になります。

### 決定事項
* 低レイヤのデータ転送、バッファリング、シリアライズの処理をすべて `Rettle::Network` クラス内にカプセル化する。
* 以下の統一された同期チャネルインターフェースを提供する:
  * `read`: チャネルから次のオブジェクトを取得して返す。ストリーム終了時（EOF）は `nil` を返す。
  * `write(data)`: 必要に応じてシリアライズを行いチャネルへ送信する。バッファ容量が飽和している場合はブロックする。
  * `close`: チャネルの送信端を閉じ、下流コンシューマへ完了を通知する。
* 各タスクは `Task#send`（内部で `Network#write` を呼出）および `Task#each_recv`（`read` が `nil` になるまで反復処理）を通じてのみネットワーク層とやり取りする。

### 結果・影響
* **メリット**:
  * ETL のビジネスロジックとデータ転送メカニズムの完全な疎結合化。
  * 初期化時にトランスポート種別を指定するだけで、スレッド間、プロセス間、将来のネットワークソケット間をシームレスに切り替え可能。
  * モックトランスポートを使用したユニットテストの容易化。
* **デメリット**:
  * 単一メモリ空間内での直接変数受け渡しと比較して、わずかな間接参照オーバーヘッドが発生する。

## ADR-NET-002: デュアル並行処理トランスポート戦略 (`:queue` と `:pipe`)

### ステータス
承認済み (Accepted)

### コンテキスト
Rettle パイプラインはマルチスレッド実行とマルチプロセス実行の双方をサポートします:
1. マルチスレッド実行は、プロセスメモリの共有、低レイテンシ、オブジェクトコピー不要という利点があります。
2. マルチプロセス実行は、タスクを独立した OS プロセスに分離し、CPU バウンドな処理における Ruby GVL の制約を回避し、プロセス障害の分離を実現します。

単一の転送メカニズムでは両方のシナリオに最適化できません。インメモリキューはプロセス境界を越えられず、プロセス間パイプはスレッド間通信には不要なシリアライズオーバーヘッドを生じさせます。

### 決定事項
* `type` 引数で選択可能な2つのファーストクラス・トランスポート実装を提供する:
  1. **スレッド転送 (`type: :queue`)**:
     * `Thread::SizedQueue.new(256)` をバックエンドに使用。
     * シリアライズやコピーのオーバーヘッドがない純粋なインメモリ動作。
     * キューが256件に達した際に呼び出し元スレッドを一時停止することで自動バックプレッシャーを実現。
  2. **プロセス転送 (`type: :pipe`)**:
     * `IO.pipe`（単方向匿名 Unix パイプ）をバックエンドに使用。
     * フォークされた子プロセスに適したクリーンなプロセス間分離。
     * 下流リーダーの処理が遅い場合、OS カーネルレベルのパイプバッファブロックによるバックプレッシャーを実現。

### 結果・影響
* **メリット**:
  * スレッドベースのパイプラインにおいてシリアライズ不要の最適パフォーマンスを維持。
  * マルチプロセス・パイプラインにおいて安全でメモリが分離されたストリーミングを実現。
  * どちらの並行実行モードでも一貫したバックプレッシャーが働き、メモリ枯渇（OOM）を確実に防止。
* **デメリット**:
  * `:pipe` を通じて渡すデータは `Marshal` でシリアライズ可能である必要がある。

## ADR-NET-003: 長さプレフィックス付き16進数エンコード Marshal ワイヤープロトコル

### ステータス
承認済み (Accepted)

### コンテキスト
ストリーム指向のトランスポート（`IO.pipe` や将来の TCP ソケット）で任意の Ruby オブジェクトをストリーミングする場合、バイトストリームにはメッセージの区切りが存在しません。このプロトコルは以下を満たす必要があります:
1. データの欠損やパケット分断を起こさず、メッセージフレームの境界を確実に認識できること。
2. 任意の複雑な Ruby オブジェクト（ハッシュ、カスタムモデル、配列など）を、区切り文字との衝突なしに安全にシリアライズできること。
3. 送信側がストリームを閉じた際に正常終了を検知できること。

### 決定事項
* ストリーム転送において、明示的なバイト長プレフィックスと16進数エンコードされた `Marshal` シリアライズによるフレーミングプロトコルを採用する:
  1. **シリアライズ**: `Marshal.dump(data)` でバイト列に変換後、`.unpack("h*")[0]` で16進数文字列に変換。
  2. **フレーミングヘッダ**: ペイロードのバイト長を ASCII 整数文字列とし、改行コード（`\n`）で区切って送信。
  3. **ペイロード送信**: 16進数文字列をそのまま送信。
  4. **受信**: `IO#readline` で長さヘッダを読み取り、`IO#read(size)` で正確に `size` バイトを取得。`[mstr].pack("h*")` でデコード後、`Marshal.load` でオブジェクトを復元。
  5. **終了検知**: `IO#readline` が `EOFError` を発生させた際に `nil` を返す。

### 結果・影響
* **メリット**:
  * ペイロード内容と区切り文字の衝突が原理的に発生しない。
  * 途中の断片化読み込みに対しても堅牢。
  * 16進数表現によりストリームの目視確認やデバッグが容易。
* **デメリット**:
  * 16進数化により通信路上のペイロードサイズが2倍になり、エンコード・デコードの CPU 負荷が増加する。
  * 高スループット環境に向けた最適化として、将来的に生バイナリ（4バイト Big-Endian 長プレフィックス）への移行ロードマップを維持する。

## ADR-NET-004: ライフサイクル管理、EOF 伝播、および単方向ティアダウン

### ステータス
承認済み (Accepted)

### コンテキスト
ストリーミング ETL パイプラインにおいて、上流タスクの処理完了時に下流タスクを安全に終了させる必要があります。ファイルディスクリプタを開いたままワーカーのスレッドやプロセスが残留すると、デッドロックやリソース枯渇、パイプラインのハングアップが発生します。

### 決定事項
* 厳格な単方向ストリーミングライフサイクルを適用する:
  * 上流タスクは下流チャネルへの書き込み（Writer）専用として振る舞う。
  * 下流タスク（`:transform`, `:load`）が自身の受信用チャネルを初期化・保持する。
  * `Rettle#connect` 時に上流タスクへ受信側タスクのネットワークインスタンスが渡される。
* **安全な終了シーケンス (Graceful Teardown)**:
  * タスク実行ブロックを抜けた際、`Rettle#connect` は接続されたすべての下流ネットワークの `close` を自動的に呼び出す。
  * `:pipe` の `close` は書き込み側 `@fds[1]` を閉じる。バッファ内のデータがすべて読み切られると、受信側 `@fds[0]` で `EOFError` が発生する。
  * `:queue` の `close` は `SizedQueue#close` を呼び出す。キューに残ったアイテムがすべて消費された後、`pop` は `nil` を返す。
* 下流タスクは `each_recv` ループ内で `read` が `nil` を返すことで自然に反復を終了する。

### 結果・影響
* **メリット**:
  * ペイロードと衝突するリスクのある独自の終了マーカートークン（例: `:eof` シンボル）が不要。
  * スレッドの残留やパイプの解放漏れがなく、予測可能で自動的なリソース解放を実現。
* **デメリット**:
  * 単一入力の原則（各チャネルに対して書き込み側は常に1つ）を厳格に順守する必要がある（複数の上流がある場合に途中でチャネルが閉じられることを防ぐため）。
