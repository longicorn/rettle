* **日付**: 2026-11-21
* **決定者**: Rettle コアコントリビューター
* **参照**: `docs/task/prd.md`, `lib/rettle/task*.rb`, `lib/rettle/network.rb`

---

## 1. コンテキストと課題

Rettle は Ruby によるコードファーストの ETL フレームワークです。ETL パイプラインは、有向非巡回グラフ（DAG）として構成される個別のデータ抽出・変換・出力ステップから構成されます。

`Rettle::Task` サブシステムの仕様化および改善にあたり、以下の主要なアーキテクチャ上の課題を解決する必要があります。
1. **並行性と拡張性**: パイプライン開発者向けの統一的でシンプルな DSL を保ちつつ、タスクの実行定義を基盤となる並行性メカニズム（スレッド、プロセス、アクター）からどのように分離するか。
2. **バックプレッシャーとストリーミング通信**: メモリの無制限な増大や複雑な同期プロトコルを招くことなく、タスク間でストリーミングデータをどのように転送するか。
3. **監視とライブラリ親和性の高いエラー処理セマンティクス**: 並行動作するタスクの障害を検知した際、プロセスを強制終了（`exit`）させずに、呼び出し元のジョブ基盤（ActiveJob, Solid Queue, Rake 等）へ例外をどのように安全に伝播させるか。
4. **スレッドセーフティとプロセスグローバル状態の非汚染**: マルチスレッドワーカー環境において、カレントディレクトリ等のプロセス共通状態を変更せずにタスクヘルパーを安全に並行実行するにはどうすべきか。
5. **ストリーミングダウンローダーとキャッシュ戦略**: 大容量データをメモリ枯渇を招かずに高信頼に取得し、不要な再ダウンロードをどう回避するか。

## 2. 決定事項の要約

| 決定領域 | 採用したアプローチ | 主な選定理由 |
| :--- | :--- | :--- |
| **実行モデル** | プラガブルなバックエンドを持つ抽象処理単位（現行: `Thread`） | タスク処理ロジックと並行実行機構を分離。パイプライン DSL を変更することなく、将来的なマルチプロセス（`fork`）や `Ractor` への拡張を可能にするため。 |
| **データフローとバックプレッシャー** | `Rettle::Network`（`SizedQueue` / `IO.pipe`）による有界チャネル | 送信元タスクを自然にブロックすることでバックプレッシャーを実現し、高スループット時におけるメモリ枯渇（OOM）を防止するため。 |
| **パイプライン監視とエラー伝播** | IPC Watchdog パイプによるフェイルファスト監視と例外再送出 | タスク障害時に他タスクを直ちに停止し、`exit` を呼ばずに最初の例外を呼び出し元へ再送出して上位のリトライや通知に委ねるため。 |
| **スレッドセーフティと状態非汚染** | `Dir.chdir` の全面撤廃とインスタンスごとの `extend` 組み込み | Solid Queue 等のマルチスレッドワーカーにおけるプロセスグローバルな競合を回避し、クラス汚染を防止するため。 |
| **ダウンローダーとデータ取得** | ディスク直接ストリーミング、リダイレクト/リトライ追従、条件付きキャッシュ（304） | ギガバイト級ダウンロード時の OOM を防止し、通信の耐障害性を高め、更新のないデータの冗長な再ダウンロードをスキップするため。 |
| **パラメータ注入と結果収集** | 明示的なパラメータ注入と `emit` / `results` によるメッセージパッシング | 厳格な Share-nothing 分離を徹底し、共有クロージャによる競合状態を排除。マルチプロセス（`fork`）や `Ractor` 下でも同一のセマンティクスを保証するため。 |

## 3. アーキテクチャ決定事項

### 3.1 決定 1: 並行性バックエンドから分離された抽象処理単位としての Task

#### コンテキスト
`Task` は ETL パイプライン内の論理的なステージ（`:extract`, `:transform`, `:load`）を表します。初期の Rettle 実装では、タスクは標準的な Ruby スレッド上で並行動作していました。しかし、ETL ワークロードの特性によって最適な並行処理モデルは異なります。
* I/O バウンドなパイプラインは、軽量なスレッドによる恩恵を受けます。
* CPU 集中型のデータ変換（パース、圧縮、暗号化処理など）は、Ruby の GVL（Global VM Lock）の制約を受けるため、マルチプロセス（`fork`）やアクターモデル（`Ractor`）による並行実行が有効です。

#### 決定事項
**タスク定義**（実行ブロック、ストリーミング I/O API、ドメインヘルパーモジュール）を**実行バックエンド（Concurrency Backend）**から分離します。
1. **インターフェースの安定性**: 開発者は統一された DSL（`define_task`, `each_recv`, `send`）およびタスク種別ごとのヘルパー（`TaskCommon`, `TaskExtract`, `TaskTransform`, `TaskLoad`）を用いてタスクを定義します。
2. **現行のベースライン**: 各タスクは `Task#run` によって生成される独立した Ruby `Thread` インスタンス上で動作します。
3. **プラガブルなアーキテクチャ**: 並行実行モデルを交換可能な実行戦略（Execution Strategy）として位置づけます。パイプライン定義やデータ処理ロジックを変更することなく、将来的にプロセスベースの `fork` や `Ractor` などのバックエンドを追加・差し替え可能とします。

#### 結果・影響
* **メリット**:
  * ETL ビジネスロジックと並行処理機構の関心の分離が明確になる。
  * 現在および将来の Rettle バージョンにおいてユーザー向け API の安定性が維持される。
  * ワークロード特性（I/O 集中型 vs CPU 集中型）に応じた実行戦略のスケールが可能になる。
* **トレードオフ**:
  * 将来のマルチプロセスやアクター対応を見据え、タスク実装側でインメモリスレッド特有の前提（共有グローバル変数の直接書き換えなど）を避ける必要がある。

---

### 3.2 決定 2: 有界チャネルと組み込みバックプレッシャーによるタスク間通信

#### コンテキスト
パイプラインは、抽出タスクから複数の変換ステージを経てロード先へと連続的にデータをストリーミングします。上流タスクの生成速度が下流タスクの処理速度を上回る場合、無制限のバッファリングはメモリの肥大化やプロセスの異常終了（Out of Memory）を引き起こすリスクがあります。

#### 決定事項
タスク間の全通信を `Rettle::Network` チャネル層を介して抽象化します。
1. **有界バッファ**: デフォルトのインメモリ通信では、固定バッファサイズ（デフォルト `QUEUE_SIZE = 256`、設定可能）を持つ Ruby の `SizedQueue` を使用します。
2. **自動バックプレッシャー**: 下流キューが上限に達した場合、送信側タスクの `Task#send` は空きができるまで自動的にブロックされます。
3. **IPC チャネルのサポート**: プロセス境界を越える通信やファイルディスクリプタを介した連携のために、Unix `IO.pipe` と 16 進エンコードされた `Marshal` シリアライゼーションを利用する `:pipe` モードを提供します。
4. **ライフサイクルシグナル**: 上流タスクは処理完了時に下流チャネルをクローズ（`close`）することで、下流の `Task#each_recv` イテレータにストリーム終了（`nil`）を伝達します。

#### 結果・影響
* **メリット**:
  * ストリームの規模やタスク間の処理速度差に関わらず、メモリ使用量を一定かつ予測可能な範囲に抑制できる。
  * アプリケーションコード側で明示的なフロー制御を実装することなく、ランタイムによって透過的にバックプレッシャーが提供される。
  * インメモリキューとプロセス間パイプの両方に対応するシンプルなシリアライゼーションモデル。
* **トレードオフ**:
  * `:pipe` における小さなオブジェクトの高頻度なシリアライズ・デシリアライズは、インメモリキューに比べて CPU オーバーヘッドが生じる。

---

### 3.3 決定 3: IPC Watchdog パイプによるフェイルファスト監視とライブラリ例外再送出

#### コンテキスト
並行動作する分散またはマルチスレッドの ETL パイプラインにおいて、一部のタスクで捕捉されない例外が発生した際、他タスクが処理を継続すると、中途半端なデータが下流に書き込まれたり、上流タスクが無限に待機したりして、外部データストアに不整合なデータが残る恐れがあります。また、Rettle が ActiveJob や Solid Queue などのバックグラウンドワーカー内で実行される場合、ライブラリ内で `exit` してしまうとワーカープロセス自体が停止し、フレームワークのリトライ機構や障害監視が動作しなくなります。

#### 決定事項
Rettle は IPC Watchdog パイプによるフェイルファスト（Fail-Fast）監視モデルを採用し、ライブラリとして例外を呼び出し元へ伝播します。
1. **Watchdog ファイルディスクリプタ**: パイプライン起動時に専用の IPC パイプ（`@watchdog_fd`）を初期化し、すべてのタスクに渡します。
2. **即時アラート送信**: いずれかのタスクの実行ブロック内で捕捉されない例外が発生した場合、タスクはエラーを捕捉し、Watchdog パイプにアラートフラグ（`"1"`）を書き込み、例外インスタンスを保持します。
3. **フェイルファスト停止と例外再送出**: メインの監視処理は Watchdog パイプを監視します。アラートを受信すると直ちに他タスクを停止（稼働中のスレッド／プロセスをクリーンに停止）し、最初に発生した例外を `Rettle#run` / `run!` の呼び出し元へ再送出（re-raise）します。
4. **`exit` の不使用**: ライブラリ内部で `Kernel.exit` を呼び出すことは一切行わず、プロセスやジョブの制御権を呼び出し元アプリケーションに委ねます。

#### 結果・影響
* **メリット**:
  * 不整合または破損した ETL データが外部ストレージにコミットされるのを確実に防止する。
  * Rails / ActiveJob のリトライ制御（`retry_on`）やエラー監視（Sentry 等）、自動テストとのシームレスな統合が可能となる。
  * 標準的な Unix ファイルディスクリプタを利用するため、スレッド実行でもプロセス実行でも統一的に機能する。
* **トレードオフ**:
  * パイプライン稼働中の個別タスク単位での部分リトライは行われず、エラー発生時はパイプライン実行全体が中断されるため、リトライ処理はパイプラインオーケストレーション単位で行う必要がある。

---

### 3.4 決定 4: スレッドセーフティとプロセスグローバル状態の非汚染

#### コンテキスト
Solid Queue などのマルチスレッドワーカーや並列テスト実行環境では、プロセスのカレントディレクトリ（`Dir.pwd`）は全スレッドで共有されるプロセスグローバルなリソースです。
旧来の実装では `TaskExtract#download` や `git_clone` で `Dir.chdir(dir)` を使用していたため、別スレッドで同時に動作する他のジョブのファイル相対パス解決が破壊される深刻な競合リスクが存在しました。また、クラスレベルのモジュールインクルードは `Rettle::Task` クラス全体を汚染する問題がありました。

#### 決定事項
1. **`Dir.chdir` の全面撤廃**: `TaskExtract#download`, `after_download`, `git_clone` から `Dir.chdir` の呼び出しを完全に撤廃します。
2. **明示的なディレクトリ・パス指定**:
   * ファイル・ディレクトリ操作は `File.join(dir, ...)` による明示的パス指定を使用します。
   * Git 操作は `git -C <dir>` オプションを用い、カレントディレクトリを変更せずに指定ディレクトリに対して実行します。
   * アーカイブ解凍（ZIP、`.tar.gz` 等）も展開先ディレクトリを明示指定して実行します。
3. **インスタンス単位の `extend` 適用**: `Task#initialize` において、クラス汚染を避けるためインスタンスに対して `extend` で種別固有のヘルパーを付与します。

#### 結果・影響
* **メリット**:
  * 単一プロセス内のマルチスレッド環境（Solid Queue, Sidekiq, 並列テスト等）で複数のパイプラインを完全にスレッドセーフに並行実行できる。
  * プロセスグローバルな副作用が排除され、安全性が飛躍的に向上する。
* **トレードオフ**:
  * 外部コマンド呼び出しやパス解決を行うすべてのヘルパーにおいて、明示的な対象ディレクトリ引数の指定が必須となる。

---

### 3.5 決定 5: ストリーミングダウンローダーとキャッシュ戦略

#### コンテキスト
従来のダウンローダーは `Net::HTTP.get(uri)` を使用しており、レスポンス全体を一度にメモリへ読み込んでいました。これにより数百MB〜数GB規模のデータを扱う際にメモリ消費が急増し、OOM（Out of Memory）キルを招くリスクがありました。また、HTTP リダイレクト（301/302）の未追従、タイムアウトやリトライの欠如、未更新ファイルの毎回全取得による帯域と処理時間の浪費という課題がありました。

#### 決定事項
1. **ディスクへの直接ストリーミング**: `Net::HTTP` のチャンク読み込み（`request_get` + `read_body`）を用いて、レスポンスデータを直接ファイルへストリーミング書き込みし、メモリフットプリントを常に最小・一定に維持します。
2. **ネットワーク耐障害性**:
   * HTTP リダイレクト（301, 302, 307, 308）を上限回数（例: 最大 5 回）まで安全に自動追従します。
   * 接続および読み取りタイムアウトを設定可能とします。
   * 一時的な通信エラーに対する簡易リトライ機能を提供します。
3. **メタデータ取得と条件付きリクエスト（304 判定）**:
   * ダウンロード結果のメタデータ（`etag`, `last_modified`, `content_length`, `sha256` 等）を保持・提供します。
   * `If-None-Match` や `If-Modified-Since` ヘッダーを用いた条件付きリクエストをサポートし、HTTP 304（Not Modified）返却時にはダウンロードおよび後続タスクを安全にスキップできる仕組みを導入します。
4. **アーカイブ対応の拡充**:
   * ZIP だけでなく `.tar.gz` や `.gz` 等のアーカイブ形式にも対応し、明示的パス指定で安全に解凍します。

#### 結果・影響
* **メリット**:
  * ギガバイト級の大容量ファイルでもメモリを消費せず安定して処理可能。
  * クラウドストレージ（S3 等のリダイレクト）や不安定なネットワーク環境での堅牢性が大幅に向上。
  * 304 キャッシュ判定により、不要なネットワーク転送とパイプライン再実行を大幅に削減できる。
* **トレードオフ**:
  * ダウンローダーの実装が `Net::HTTP.get` より複雑になる。
  * キャッシュヒット時に後続タスクをスキップするための条件分岐や通知セマンティクスがパイプライン側に必要となる。

### 3.6 決定 6: 明示的なパラメータ注入と emit による Share-nothing な結果収集

#### コンテキスト
ETL パイプラインにおいて、タスクは実行時設定パラメータ（対象エンドポイント、日付範囲、バッチサイズ等）を必要とすることが多く、またテスト実行時や上位ジョブ基盤への通知のために、実行サマリーや収集レコードを呼び出し元へ返却する必要があります。
従来、テストコードやスクリプト等では、タスク定義ブロックの外側にあるローカル変数を Ruby のクロージャで捕捉・更新するパターン（例: 外側で定義した `received = []` への `<<` 追加）に依存することがありました。このパターンは同一メモリ空間を共有するマルチスレッド実行では一見動作しますが、以下の深刻な問題を抱えています：
1. **プロセス分離（`fork`）時の破綻**: タスクを独立した OS プロセスで実行した場合、メモリ空間は完全に分離されます。子プロセス内で行われた外側変数の変更は親プロセスへ反映されず、プロセス終了とともに消失するため、テストや呼び出し元の処理が暗黙的に破綻します。
2. **マルチスレッド環境での競合状態（Race Condition）**: 複数のタスクスレッドから保護機構なしに共有クロージャ変数を読み書きすると、競合状態が発生し非決定的な不具合の原因となります。
3. **カプセル化の破壊**: 暗黙的なクロージャ捕捉は、タスク定義を外側のスコープと強く結合させ、再利用性や並行実行バックエンドの変更容易性を著しく損ないます。

#### 決定事項
1. **共有可変状態の厳格な禁止**: タスク境界を越えた暗黙のクロージャ変数のミューテーション、および親パイプラインとの間での変数共有を明示的に禁止します。タスクはメッセージパッシングのみで通信する Share-nothing な処理単位として扱います。
2. **明示的なパラメータ注入**:
   * タスク定義時（`define_task`）に初期パラメータ（例: `define_task(:name, params: { ... })`）を明示的に渡せるインターフェースを提供します。
   * タスク実行ブロック内からは、タスクインスタンスのアクセサ（`task.params`）を通じて安全にパラメータへアクセス可能とし、外部変数の捕捉を不要にします。
3. **親パイプライン向けチャネルとしての `task.emit`**:
   * タスクから親パイプラインへ結果ペイロードを送信するための `task.emit(payload)` メソッドを導入します。
   * この通信チャネルは既存の `Rettle::Network` 抽象（スレッド時は有界キュー、プロセス/fork時は IPC パイプと直列化）を活用して実現します。
4. **`etl.results` への結果集約**:
   * パイプライン実行完了時（`run` / `run!` 終了時）に、親スーパーバイザが全タスクから `emit` されたデータを集約し、`etl.results` として呼び出し元に提供します。

#### 結果・影響
* **メリット**:
  * **並行性バックエンド間でのセマンティクス統一**: `Thread`、`fork`、`Ractor` いずれの実行バックエンドであっても、パイプラインとテストコードが全く同じセマンティクスで動作する。
  * **並行処理バグの排除**: 共有メモリへの無保護な書き込みによる競合状態やデータ消失が根本から排除される。
  * **テスト容易性の向上**: 単体テスト・結合テストにおいて、アキュムレータ配列を外側で定義することなく、`etl.results` を通じて宣言的に結果を検証可能となる。
* **トレードオフ**:
  * マルチプロセス実行に対応するため、`task.emit` で送出するオブジェクトは直列化可能（Marshal 可能）である必要がある。
  * 従来のクロージャに依存したコードやテストケースは、`params` および `task.emit` を使用する形へリファクタリングが必要となる。
