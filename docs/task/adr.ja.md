## 1. コンテキストと課題

Rettle は Ruby によるコードファーストの ETL フレームワークです。ETL パイプラインは、有向非巡回グラフ（DAG）として構成される個別のデータ抽出・変換・出力ステップから構成されます。

`Rettle::Task` サブシステムの仕様化にあたり、以下の 3 つの基礎的なアーキテクチャ上の課題を解決する必要があります。
1. **並行性と拡張性**: パイプライン開発者向けの統一的でシンプルな DSL を保ちつつ、タスクの実行定義を基盤となる並行性メカニズム（スレッド、プロセス、アクター）からどのように分離するか。
2. **バックプレッシャーとストリーミング通信**: メモリの無制限な増大や複雑な同期プロトコルを招くことなく、タスク間でストリーミングデータをどのように転送するか。
3. **監視とエラー処理セマンティクス**: パイプライン全体のデータ整合性を維持するために、並行動作するタスクの障害をどのように検知・処理すべきか。

---

## 2. 決定事項の要約

| 決定領域 | 採用したアプローチ | 主な選定理由 |
| :--- | :--- | :--- |
| **実行モデル** | プラガブルなバックエンドを持つ抽象処理単位（現行: `Thread`） | タスク処理ロジックと並行実行機構を分離。パイプライン DSL を変更することなく、将来的なマルチプロセス（`fork`）や `Ractor` への拡張を可能にするため。 |
| **データフローとバックプレッシャー** | `Rettle::Network`（`SizedQueue` / `IO.pipe`）による有界チャネル | 送信元タスクを自然にブロックすることでバックプレッシャーを実現し、高スループット時におけるメモリ枯渇（OOM）を防止するため。 |
| **パイプライン監視** | IPC Watchdog パイプによるフェイルファスト監視 | タスク障害時にパイプライン全体を直ちにアトミック終了させ、不整合や中途半端なデータ書き込みを防ぐため。 |

---

## 3. アーキテクチャ決定事項

### 3.1 決定 1: 並行性バックエンドから分離された抽象処理単位としての Task

#### コンテキスト
`Task` は ETL パイプライン内の論理的なステージ（`:extract`, `:transform`, `:load`）を表します。初期の Rettle 実装では、タスクは標準的な Ruby スレッド上で並行動作していました。しかし、ETL ワークロードの特性によって最適な並行処理モデルは異なります。
* I/O バウンドなパイプラインは、軽量なスレッドによる恩恵を受けます。
* CPU 集中型のデータ変換（パース、圧縮、暗号化処理など）は、Ruby の GVL（Global VM Lock）の制約を受けるため、マルチプロセス（`fork`）やアクターモデル（`Ractor`）による並行実行が有効です。

#### 決定事項
**タスク定義**（実行ブロック、ストリーミング I/O API、ドメインヘルパーモジュール）を**実行バックエンド（Concurrency Backend）**から分離します。
1. **インターフェースの安定性**: 開発者は統一された DSL（`define_task`, `each_recv`, `send`）およびタスク種別ごとのヘルパー（`TaskCommon`, `TaskExtract`, `TaskTransform`, `TaskLoad`）を用いてタスクを定義します。
2. **現行のベースライン**: 各タスクは `Task#run` によって生成される独立した Ruby `Thread` インスタンス上で動作します。
3. **プラガブルなアーキテクチャ**: 並行実行モデルを交換可能な実行戦略（Execution Strategy）として位置づけます。パイプライン定義やデータ処理ロジックを変更することなく、将来的にプロセスベースの `fork` や `Ractor` などのバックエンドを追加・差し替え可能とします。

#### 結果・影響
* **メリット**:
  * ETL ビジネスロジックと並行処理機構の関心の分離が明確になる。
  * 現在および将来の Rettle バージョンにおいてユーザー向け API の安定性が維持される。
  * ワークロード特性（I/O 集中型 vs CPU 集中型）に応じた実行戦略のスケールが可能になる。
* **トレードオフ**:
  * 将来のマルチプロセスやアクター対応を見据え、タスク実装側でインメモリスレッド特有の前提（共有グローバル変数の直接書き換えなど）を避ける必要がある。

---

### 3.2 決定 2: 有界チャネルと組み込みバックプレッシャーによるタスク間通信

#### コンテキスト
パイプラインは、抽出タスクから複数の変換ステージを経てロード先へと連続的にデータをストリーミングします。上流タスクの生成速度が下流タスクの処理速度を上回る場合、無制限のバッファリングはメモリの肥大化やプロセスの異常終了（Out of Memory）を引き起こすリスクがあります。

#### 決定事項
タスク間の全通信を `Rettle::Network` チャネル層を介して抽象化します。
1. **有界バッファ**: デフォルトのインメモリ通信では、固定バッファサイズ（`QUEUE_SIZE = 256`）を持つ Ruby の `SizedQueue` を使用します。
2. **自動バックプレッシャー**: 下流キューが上限に達した場合、送信側タスクの `Task#send` は空きができるまで自動的にブロックされます。
3. **IPC チャネルのサポート**: プロセス境界を越える通信やファイルディスクリプタを介した連携のために、Unix `IO.pipe` と 16 進エンコードされた `Marshal` シリアライゼーションを利用する `:pipe` モードを提供します。
4. **ライフサイクルシグナル**: 上流タスクは処理完了時に下流チャネルをクローズ（`close`）することで、下流の `Task#each_recv` イテレータにストリーム終了（`nil`）を伝達します。

#### 結果・影響
* **メリット**:
  * ストリームの規模やタスク間の処理速度差に関わらず、メモリ使用量を一定かつ予測可能な範囲に抑制できる。
  * アプリケーションコード側で明示的なフロー制御を実装することなく、ランタイムによって透過的にバックプレッシャーが提供される。
  * インメモリキューとプロセス間パイプの両方に対応するシンプルなシリアライゼーションモデル。
* **トレードオフ**:
  * `:pipe` における小さなオブジェクトの高頻度なシリアライズ・デシリアライズは、インメモリキューに比べて CPU オーバーヘッドが生じる。

---

### 3.3 決定 3: IPC Watchdog パイプによるフェイルファスト監視

#### コンテキスト
並行動作する分散またはマルチスレッドの ETL パイプラインにおいて、一部のタスクで捕捉されない例外やパースエラーが発生した際、他タスクが処理を継続すると、中途半端なデータが下流に書き込まれたり、上流タスクが無限に待機したりして、外部データストアに不整合なデータが残る恐れがあります。

#### 決定事項
Rettle は IPC Watchdog パイプによるフェイルファスト（Fail-Fast）監視モデルを採用します。
1. **Watchdog ファイルディスクリプタ**: パイプライン起動時に専用の IPC パイプ（`@watchdog_fd`）を初期化し、すべてのタスクに渡します。
2. **即時アラート送信**: いずれかのタスクの実行ブロック内で捕捉されない例外が発生した場合、タスクはエラーを捕捉し、Watchdog パイプにアラートフラグ（`"1"`）を書き込み、例外ログを出力します。
3. **フェイルファスト終了**: メインの監視プロセスは Watchdog パイプを監視します。アラートを受信すると直ちにパイプライン全体を終了（稼働中のスレッド／プロセスを kill）し、例外を送出して、以降の部分的なデータ処理の継続を即座に遮断します。

#### 結果・影響
* **メリット**:
  * 不整合または破損した ETL データが外部ストレージにコミットされるのを確実に防止する。
  * 標準的な Unix ファイルディスクリプタを利用するため、スレッド実行でもプロセス実行でも統一的に機能する。
  * 障害発生時の動作がシンプルで決定論的である。
* **トレードオフ**:
  * パイプライン稼働中の個別タスク単位での部分リトライは行われず、エラー発生時はパイプライン実行全体が中断されるため、リトライ処理はパイプラインオーケストレーション単位で行う必要がある。

## 接続と障害通知の補足

`connect`が返す宛先タスクへの`send`は、その入力チャネルに書き込みます。タスクの失敗時は他のタスクを停止し、元の例外を`run`の呼び出し元に伝えます。
