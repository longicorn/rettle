# アーキテクチャ決定記録 (ADR) - Rettle

[English](adr.md)

このドキュメントは、ETLフレームワーク「Rettle」において採用されたアーキテクチャおよび設計上の意思決定を記録したものです。

---

## ADR-001: パイプラインアーキテクチャとタスク並列実行

### 状態
承認済み (Accepted)

### 背景
データ取り込みやETL処理は、データ取得（Extract）、変換・正規化（Transform）、保存・書き込み（Load）という明確なフェーズに分割されます。単一の順次処理スクリプトでは、各フェーズの密結合、HTTPダウンロードやDBクエリなどのI/Oバウンドな処理によるレイテンシの増大、エラー境界の管理の難しさが生じます。

### 決定
* ETLワークフローを単一責任のタスク（`Extractor`, `Transformer`, `Loader`）に分割する**パイプラインアーキテクチャ**を採用する。
* 各タスクを独立した実行コンテキスト（主にRubyスレッド `Thread`、必要に応じてフォークプロセス `Process`）で並列実行する。
* 通信路の初期化、スレッドのjoin、終了検知、パイプのクローズ処理などの並列同期に伴う複雑性を `Rettle` エンジン内部に隠蔽し、利用者が直感的なDSLでタスク定義と接続を行えるようにする。

### 影響・結果
* **メリット**: I/Oバウンドな処理における高いスループット、各フェーズの疎結合化、読みやすくテストしやすいコード構造。
* **デメリット**: 内部実装において競合状態やデッドロック、ストリーム終了検知などの並行プログラミングの複雑性に対処する必要がある。

## ADR-002: ストリーミング通信とバックプレッシャー制御

### 状態
承認済み (Accepted)

### 背景
数百MBから数十GB規模の大規模データを処理する際、全データをメモリ上に一括読み込みするとメモリ枯渇（OOM）が発生します。また、無制限なプロデューサー・コンシューマーモデルでは、抽出（Extract）が下流の変換（Transform）やDB格納（Load）を圧倒してメモリを圧迫します。

### 決定
* タスク間通信路（`Rettle::Network`）として、Ruby標準のストリーミングプリミティブである `IO.pipe`（UNIXパイプセマンティクス）およびバッファ制限付きキュー（`SizedQueue`、デフォルト `QUEUE_SIZE = 256`）を採用する。
* 下流タスクのバッファが満杯になった場合、上流タスクの送信処理が自動的にブロック（待機）するOS/ランタイムのバックプレッシャー機構を利用する。

### 影響・結果
* **メリット**: データサイズに関わらずメモリ使用量を一定かつ最小限に維持でき、OOMを防止。自然なストリーミング処理を実現。
* **デメリット**: エラーによるタスク異常終了時にデッドロックを防ぐため、EOF（終端記号）の適切な伝播とパイプのクローズ処理を厳密に管理する必要がある。

## ADR-003: 単一入力の原則（合流・Fan-in の非サポート）

### 状態
承認済み (Accepted)

### 背景
データパイプラインを有向非巡回グラフ（DAG）として設計する場合、理論的には分岐（1対多のFan-out）と合流（多対1のFan-in）の両方が考えられます。しかし、複数入力の合流を許容すると、すべての上流タスクの終了同期、デッドロック回避、複数チャネルの多重化処理が極めて複雑になります。

### 決定
* **単一入力の原則**を徹底し、各タスク（特に `Loader`）は「単一の上流タスクからのみデータを受け取る」制約を設ける。
* **サポートするフローパターン**:
  * 直列フロー: `Extractor -> Transformer -> Loader` (または `Extractor -> Loader`)
  * チェーンフロー: `Extractor -> Transformer 1 -> Transformer 2 -> Loader`
  * 分岐フロー (Fan-out): `Extractor -> Transformer 1` および `Extractor -> Transformer 2`
* **非サポート（禁止）パターン**:
  * 合流フロー (Fan-in): `(Transformer 1, Transformer 2) -> Loader` は明示的に非サポートとする。
* 複数の分岐データを格納したい場合は、分岐ごとに独立した `Loader` を接続する構成とする。

### 影響・結果
* **メリット**: パイプラインのライフサイクル、終了検知、リソース開放が極めてシンプルかつ堅牢に保たれる。
* **デメリット**: 複数ストリームの結合（Join）処理が必要な場合は、単一のTransformer内で処理するか、別々のパイプライン間で連携を設計する必要がある。

## ADR-004: Ruby標準スタック、テスト駆動方針、開発規約

### 状態
承認済み (Accepted)

### 背景
Ruby on Railsプロジェクトへの組み込みやすさとポータビリティを担保するため、外部依存は最小限に抑える必要があります。また、長期的な保守性と品質を維持するために、コードスタイルとテスト方針を統一します。

### 決定
1. **技術スタック**:
   * Ruby 3.x を対象とし、コアランタイムは Ruby 標準ライブラリ（`csv`, `io/wait`, `socket` など）を中心に構成する。
   * コア機能における重量級の外部依存gemを避ける。
2. **テスト方針**:
   * テスティングフレームワークとして `Minitest` を採用する。
   * **Test-First（テストファースト）方針**: 新機能実装やバグ修正時は、必ず先に失敗するテストを作成しRedを確認してから実装を行う。
   * テストファイルは `test/test_{src_file}.rb` の命名規則に従い `test/` 配下に配置する。
3. **コーディングスタイルとドキュメント**:
   * すべてのRubyファイル先頭に `# frozen_string_literal: true` を記述する。
   * インデントは2スペース、命名規則はRuby標準（メソッド/変数は `snake_case`、クラス/モジュールは `PascalCase`）を徹底する。
   * 公開APIには YARD 形式でコメントを付与する。
   * 静的型チェックを支援するため、`sig/` 配下に RBS 型定義（`sig/rettle.rbs` 等）を整備・保守する。

### 影響・結果
* **メリット**: 依存関係のコンフリクトを回避し、Railsアプリケーション等へ容易に組み込み可能。高いコード品質とテスト網羅性を維持。
* **デメリット**: ファイルダウンロードや解凍などのヘルパー機能について、標準ライブラリまたは厳選された軽量ライブラリを用いて自前で抽象化を構築する必要がある。
