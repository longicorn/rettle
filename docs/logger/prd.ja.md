# 要求仕様書 (PRD) - Rettle Logger サブシステム

[English](prd.md)

## 1. 概要と目的

### 1.1 概要
Logger サブシステムは、Rettle ETL フレームワークに対して統一的かつ設定可能でスレッドセーフなロギング機構を提供します。Ruby 標準の `Logger` およびアプリケーション層のロガー（`Rails.logger` など）とシームレスに連携する標準的なロギング抽象化を確立し、これまでの `puts` や `p` によるアドホックな標準出力/エラー出力を構造化されたコンテキスト付きログへと刷新します。

### 1.2 目的と背景
バッチや ETL ワークフロー（機能要望 #5 に挙げられている ActiveJob / Solid Queue 等を用いた Rails バッチ基盤など）において、ジョブには可観測性と制御可能なログ出力が不可欠です。従来の実装では、内部例外や実行診断情報が標準出力に直接印字されるか、あるいは抑制されていたため、集約ログ基盤との連携や並行タスク実行の追跡、ログレベルの制御が困難でした。

本サブシステムは以下の目的を達成します：
* **ロギングの標準化**: Rettle 内のハードコードされた `puts` や `p` の呼び出しを、設定可能なロガーインターフェースに置き換えます。
* **フレームワーク非依存**: Rails への直接的な依存を持たず、Ruby 標準の `Logger` で即座に動作しつつ、`Rails.logger` やカスタムロガーの注入を容易に可能にします。
* **タスク実行のコンテキスト可観測性**: ログメッセージにタスクのメタデータ（`type` および `name`）を自動的に付与し、マルチスレッドで並行動作するタスクのログを容易に追跡可能にします。
* **開発者に扱いやすい API**: 簡潔に記述できるショートハンド（`task.logger("message")`）と、標準的なログレベル別メソッド（`task.logger.info("message")`）の双方をサポートします。

## 2. 対象ユーザーとスコープ

### 2.1 対象ユーザー
* **Ruby / Rails 開発者**: アプリケーション標準に準拠した統一ログ出力を必要とするバックグラウンドジョブやデータパイプラインを構築するエンジニア。
* **運用・信頼性エンジニア**: 並行バッチ実行の監視、タスク単位の例外診断、および外部ログ収集基盤へのログ配信を行うエンジニア。

### 2.2 スコープ内（In Scope）
* **設定レイヤー**:
  * クラスレベルのグローバル設定（`Rettle.logger = ...`）
  * インスタンスレベルの設定オーバーライド（`Rettle.new(logger: ...)`）
  * 未設定時の安全なデフォルト動作（`Logger.new($stdout)`）
* **タスク向けロギングインターフェース（`Task#logger`）**:
  * ショートハンドメソッド呼び出し: `task.logger(message, level: :info)`
  * オブジェクトアクセサ形式の呼び出し: `task.logger.info(...)`, `task.logger.warn(...)`, `task.logger.error(...)`, `task.logger.debug(...)`
  * タスクコンテキストの自動付与: `[Rettle][<type>:<name>] <message>`
* **フレームワーク内部の可観測性**:
  * パイプラインライフサイクルログ（開始、タスクスレッド起動、正常完了）
  * エラー・障害ログ（バックトレース付きのタスク例外通知、watchdog による停止通知）
* **互換性と Duck Typing**:
  * 標準的な Ruby `Logger` インターフェース（`debug`, `info`, `warn`, `error`, `fatal`）を備えた任意のロガーとの互換性

### 2.3 スコープ外（Out of Scope）
* `ActiveSupport::Logger` や Rails gem への直接的なランタイム依存（フレームワーク非依存を維持）。
* Rettle コア内での専用データベーステーブルやリモートエンドポイントへのログ永続化（ロガー出力先の設定やカスタム Logger 実装に委譲）。
* 複雑なログフォーマット DSL や外部ログ解析プロトコルの直接実装。

## 3. 主要機能と機能マップ

| 機能領域 | 機能 | 振る舞い | 優先度 |
| :--- | :--- | :--- | :--- |
| **グローバルロガー設定** | `Rettle.logger = logger` | プロセス全体のデフォルトロガーインスタンスを設定 | 高 |
| **インスタンスロガー上書き** | `Rettle.new(logger: custom)` | 特定のパイプラインインスタンスのロガーを上書き | 高 |
| **デフォルトフォールバック** | `Logger.new($stdout)` | 設定不要で即座に標準出力へログを出力 | 高 |
| **タスク直接ログ（ショートハンド）** | `task.logger(msg, [level])` | コンテキスト付きで即座にログ出力（デフォルト: `:info`） | 高 |
| **タスクロガーオブジェクト参照** | `task.logger.info(msg)` | 自動コンテキスト付きで基底ロガーのメソッドを呼び出し | 高 |
| **コンテキストタグ付け** | `[Rettle][<type>:<name>]` | タスク種別と名前をプレフィックスとして自動付与 | 高 |
| **フレームワーク内部イベントログ** | ライフサイクルおよびエラーログ | アドホックな出力を適切なレベル付きログに置換 | 高 |

## 4. アーキテクチャと詳細仕様

### 4.1 設定階層と解決順序
ETL パイプライン実行時に使用されるアクティブなロガーは、以下の優先順位に従って解決されます：
1. **インスタンスレベル**: `Rettle.new(logger: ...)` に渡された `logger`
2. **クラスレベル**: 明示的に設定された `Rettle.logger`
3. **デフォルト**: Ruby 標準の `Logger.new($stdout)`（デフォルトログレベル: `Logger::INFO`）

```ruby
# アプリケーション初期化（Rails の config/initializers/rettle.rb など）
Rettle.logger = Rails.logger

# 個別のパイプラインインスタンスでの上書き
etl = Rettle.new(logger: custom_logger)
```

### 4.2 タスクコンテキストロギング（`Task#logger`）
タスク定義ブロック内では、`task.logger` が主要なロギングエントリーポイントとなります：

```ruby
etl.define_task(:extract, 'extract_users') do |task|
  # ショートハンド形式（デフォルトは :info）
  task.logger("Fetching user records from remote endpoint...")

  # レベル指定付きショートハンド
  task.logger("Rate limit threshold nearing capacity", level: :warn)

  # 標準的なメソッドチェーン形式
  task.logger.debug("Payload chunk received: 1024 bytes")
  task.logger.error("Failed to parse record id=42")
end
```

#### コンテキストフォーマット
タスクから呼び出された際、ロガーラッパーは自動的にメッセージ先頭へ `[Rettle][<type>:<name>]` を付与します：
```text
I, [2026-11-21T16:30:00.000000 #12345]  INFO -- : [Rettle][extract:extract_users] Fetching user records from remote endpoint...
W, [2026-11-21T16:30:05.000000 #12345]  WARN -- : [Rettle][extract:extract_users] Rate limit threshold nearing capacity
```

#### デュアルモード呼び出し仕様
`Task#logger` は両方の呼び出し形式を自然にサポートします：
* 引数が与えられた場合（`task.logger(message, level: :info)` など）: 指定されたログレベルでメッセージを直接出力します。
* 引数なしで呼び出された場合（`task.logger`）: 標準のロガーメソッド（`debug`, `info`, `warn`, `error`, `fatal`）に応答するコンテキスト付きロガープロキシを返します。

### 4.3 フレームワーク内部ロギング
Rettle パイプラインランタイムは、以下の運用イベントに設定されたロガーを使用します：
* **`DEBUG`**: 内部タスクスレッドの起動、チャネル作成、および reader/writer ストリームのライフサイクルイベント。
* **`INFO`**: パイプライン実行の開始および正常完了。
* **`WARN`**: watchdog の検知による兄弟タスクスレッドへの停止シグナル送信。
* **`ERROR`**: タスクブロック内で発生した未捕捉例外（例外クラス、メッセージ、バックトレースを含む）。

## 5. 非機能要件

### 5.1 スレッドセーフ性
* タスクは独立した Ruby `Thread` インスタンス上で並行実行されます。
* すべてのログ書き込みはスレッドセーフでなければなりません。Ruby 標準ライブラリの `Logger` は書き込みを同期化しますが、カスタムロガー使用時にも Rettle のコンテキストラッパーがスレッド間で競合する可変共有状態を持ち込まないように設計します。

### 5.2 パフォーマンスとオーバーヘッド
* 大量ストリーミング処理時のパフォーマンス低下を防ぐため、文字列連結やフォーマット処理のオーバーヘッドを最小限に抑えます。

### 5.3 外部依存ゼロ
* 本サブシステムは Ruby 標準ライブラリ（`logger`）のみに依存し、外部 gem やフレームワークへの依存関係を追加してはなりません。

---

## 6. 成功基準と検証項目

* [ ] `Rettle.logger = ...` によりクラスレベルでロガーを設定できること。
* [ ] `Rettle.new(logger: ...)` によりインスタンスごとにロガーを上書きできること。
* [ ] 未設定時にデフォルトで `Logger.new($stdout)` により実行できること。
* [ ] `task.logger("msg")` がデフォルト `:info` レベルかつ `[Rettle][<type>:<name>]` プレフィックス付きで出力されること。
* [ ] `task.logger("msg", level: :warn)` および `task.logger.warn("msg")` が適切なログレベルで出力されること。
* [ ] フレームワーク内のすべての `puts` および `p` の呼び出しが排除され、ロガー呼び出しに置き換わっていること。
* [ ] マルチスレッドによる並行タスクログ出力時にログ行の破損や同期エラーが発生しないこと。
