# プロダクト要求仕様書 (PRD) - Rettle

[English](prd.md)

## 1. プロダクト概要と背景

### 1.1. プロダクト概要
Rettleは、個人のWeb開発者がRubyおよびRuby on Railsプロジェクトで利用するために開発された、シンプルさと速度を重視したRuby製の軽量ETL（Extract, Transform, Load）フレームワークです。既存のETLツールが持つ複雑さや並列化の難しさを解消し、Rubyのエコシステム内で直感的に利用できる軽量な代替手段を提供します。

### 1.2. 背景とビジネス課題
個人開発者や少人数の開発チームがデータパイプラインを構築する際、既存ツールには以下の課題が存在していました：
* **過剰な複雑性と高い学習コスト**: 多くの既存ETLツール（Apache Airflow、Embulk等）は多機能である反面、設定が複雑で学習コストが高く、個人開発や中小規模のプロジェクトには過剰スペックとなりがちです。
* **並列処理・マルチスレッド化のハードル**: データパイプラインの各フェーズ（E, T, L）をマルチスレッドやマルチプロセスで安定して並列実行させるための実装や設定が煩雑でした。
* **Rubyエコシステムの開発体験**: Rubyエコシステム内で利用可能な選択肢が限られており（例: Kibaの開発停止）、Pythonなど他言語のツールを採用すると言語の分断や連携の手間が発生していました。
* **処理の可監査性とトレーサビリティ**: 「いつ、どのデータが取得され、どのように加工されて格納されたか」を証明するためのログ取得機構を自前で構築する必要がありました。

### 1.3. 解決策
Rettleはこれらの課題を以下の特徴で解決します：
* **シンプルなRuby DSL**: 直感的なAPIを提供し、ドキュメントを読めば迷わずETLパイプラインを記述できる高い開発体験を提供します。
* **並列処理基盤の内包**: 各ETLステップをマルチスレッドまたはマルチプロセスで並列実行し、I/Oバウンドな処理を大幅に高速化します。
* **定型処理ヘルパー群の提供**: ファイルのダウンロード、展開（ZIP解凍等）、文字コード変換、データベースへの一括インサートなど、頻出する定型処理を標準機能として提供します。
* **監査可能なロギング機構**: 実行状況、スループット、エラーを追跡できるロギング機構を標準で備え、トレーサビリティを確保します。

## 2. 対象ユーザーとスコープ

### 2.1. 対象ユーザー
* **プライマリ**: 個人開発や自社プロダクトでRuby on Railsを採用し、外部の大規模オーケストレータを立てずに高速かつ信頼性の高いデータ取り込み処理を実装したい開発者。
* **セカンダリ**: 外部依存を最小限に抑えつつ、軽量なETL機能を組み込みたいRuby開発者。

### 2.2. 対象範囲 (In Scope)
* ファイルベースのデータソース（CSV、TSV、JSONなど）からリレーショナルデータベースへのETL処理。
* バックプレッシャー制御を伴うマルチスレッド/マルチプロセスによるパイプラインの並列実行。
* ダウンロード、ファイル展開、文字コード変換、バッチエクスポートなどの再利用可能なヘルパー群。
* パイプ（`IO.pipe`）やキュー（`SizedQueue`）によるタスク間のストリーミング連携。

### 2.3. 対象範囲外 (Out of Scope)
* Apache Airflowのような大規模な分散クラスタスケジューリングおよびワークフロー管理。
* パイプライン定義や監視を行うGUIダッシュボード。
* Apache KafkaやApache Flinkのような継続的リアルタイムストリーミング処理。

## 3. コアソリューションと Feature Map

| 課題 (Core Problem) | 解決策となる機能 (Solution Feature) | 優先度 |
| :--- | :--- | :--- |
| メモリ制約下での大規模データ処理 | パイプおよびバッファ制限付きキューを用いたバックプレッシャー対応ストリーミング処理 | High |
| 複雑な設定と学習コスト | `Rettle` および `Rettle::Task` を中心とした直感的なDSL | High |
| 並列処理の手動設定の難しさ | スレッドおよびプロセスを活用した並列タスク実行基盤 (`Task#run`) | High |
| 定型ボイラープレートの実装負担 | ダウンロード、解凍、文字コード変換、バッチエクスポート等の組み込みヘルパー | Medium |
| 処理の可監査性の欠如 | 実行状態、処理件数、エラーを追跡できる標準ロギング機構 | Medium |

## 4. 主要ユーザーストーリー

### シナリオ 1: 外部CSVファイルをダウンロードしてDBへ取り込む
1. 開発者はダウンロードURLと抽出パラメータを指定して `extract` タスクを定義する。
2. 開発者は上流タスクからデータを受信し、スキーマ変換やデータ加工を行う `transform` タスクを定義する。
3. 開発者は変換後データを受け取り、対象DBへバルクインサートする `load` タスクを定義する。
4. Rettleは各タスクをパイプラインとして連結し、マルチスレッドで並列実行する。
5. ログに実行開始、件数、完了ステータスが出力される。

### シナリオ 2: 大容量データのストリーミング処理
1. 開発者はメモリに乗り切らない巨大なCSVファイルを処理するパイプラインを定義する。
2. `extract` タスクが1行ずつストリーミングで読み出し、`IO.pipe` 経由で下流へ送信する。
3. 下流の `transform` および `load` タスクが順次消費し、バックプレッシャーによりメモリ使用量を一定に抑えながら処理を完了する。

## 5. ドメインモデルとユビキタス言語

| 概念 | コード上の名称 | 説明 |
| :--- | :--- | :--- |
| **フレームワーク本体** | `Rettle` | タスクの定義、接続、実行を統括するコアエントリポイント。 |
| **タスク** | `Rettle::Task` | ETL処理の各フェーズを表す実行基本単位。独立したスレッドまたはプロセスで動作する。 |
| **抽出タスク** | `Rettle::TaskExtract` / `:extract` | 外部データソースからの取得・抽出を担当するタスク。 |
| **変換タスク** | `Rettle::TaskTransform` / `:transform` | 上流からデータを受け取り、ビジネスロジックに基づいて変換・加工するタスク。 |
| **格納タスク** | `Rettle::TaskLoad` / `:load` | 変換されたデータを最終的な書き込み先（DB等）へ格納するタスク。 |
| **ネットワーク** | `Rettle::Network` | タスク間でデータを送受信するための通信路（`IO.pipe` または `SizedQueue`）。 |
| **パイプライン** | *(概念)* | `connect` によって複数のタスクが連結されたデータフロー構造。 |
